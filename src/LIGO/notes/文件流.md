# LIGO 系统数据流向与源码导读

这份文件是按你当前的启动方式整理的：

1. `roslaunch gnss_to_enu gnss_to_enu_slam_banfu2_time_aligned.launch`
2. `roslaunch ligo mapping_avia_handsfree.launch`

它不是只讲概念，而是按“数据从哪来、在哪个文件处理、最后到哪里去”的顺序，把整条 SLAM 链路串起来。

先纠正一件事：你原来的 `文件流.md` 里把后端写成了 `Ceres Solver`，这和当前源码不一致。当前 `LIGO` 的后端是 `GTSAM + ISAM2`，相关入口在 [src/LIGO./src/NMEA_Assignment.h](/home/cclg/muti_path_creater/src/LIGO./src/NMEA_Assignment.h:1) 和 [src/LIGO./src/NMEA_Assignment.cpp](/home/cclg/muti_path_creater/src/LIGO./src/NMEA_Assignment.cpp:1)。另外，你现在这套 `avia_handsfree.yaml` 配置里 `gnss_enable: false`、`nmea_enable: true`，所以实际跑的是 `LiDAR + IMU + NMEA`，不是原始 GNSS 紧耦合那条线。

## 一张总图

`/handsfree/rtk/gnss`
-> `gnss_timestamp_compensator.py`
-> `/handsfree/rtk/gnss_time_aligned`
-> `gnss_to_enu.py`
-> `/rtk/gps_odom`
-> `ligo_mapping`
-> `sync_packages()`
-> `IMU 初始化 / 点云转交 + LiDAR 前端`
-> `NMEA / GNSS 因子图后端`
-> `/aft_mapped_to_init`、`/path`、`/Laser_map`

## 1. 启动入口先做了什么

### 1.1 GNSS 时间对齐与 ENU 转换

文件：
- [src/gnss_to_enu/launch/gnss_to_enu_slam_banfu2_time_aligned.launch](/home/cclg/muti_path_creater/src/gnss_to_enu/launch/gnss_to_enu_slam_banfu2_time_aligned.launch:1)
- [src/gnss_to_enu/scripts/gnss_timestamp_compensator.py](/home/cclg/muti_path_creater/src/gnss_to_enu/scripts/gnss_timestamp_compensator.py:1)
- [src/gnss_to_enu/scripts/gnss_to_enu.py](/home/cclg/muti_path_creater/src/gnss_to_enu/scripts/gnss_to_enu.py:1)

做的事：
- `gnss_timestamp_compensator.py` 只改时间戳，不改坐标。
- 它把原始 `/handsfree/rtk/gnss` 的 `header.stamp` 减去 launch 里给的 `offset_seconds`。
- 输出到 `/handsfree/rtk/gnss_time_aligned`。
- `gnss_to_enu.py` 订阅这个对齐后的 `NavSatFix`，把经纬高转成局部 ENU。
- 它发布 `nav_msgs/Odometry` 到 `/rtk/gps_odom`，并把轨迹写到 `/home/cclg/traj_rtk_origin.tum`。

你学习时要记住：
- 这里的作用不是“做 SLAM”，而是把 GNSS 变成 `LIGO` 能直接拿来融合的局部坐标。
- `gnss_to_enu.py` 默认 `use_auto_datum=true`，所以原点通常由第一帧有效 GNSS 自动设定。

### 1.2 LIGO 建图节点

文件：
- [src/LIGO./launch/mapping_avia_handsfree.launch](/home/cclg/muti_path_creater/src/LIGO./launch/mapping_avia_handsfree.launch:1)

- 开启 RViz 可视化。

## 2. 参数从哪里来

文件：
- [src/LIGO./src/parameters.cpp](/home/cclg/muti_path_creater/src/LIGO./src/parameters.cpp:1)

这里是整个程序的“配置中枢”：
- `common/lid_topic` -> 默认 `/livox/lidar`
- `common/imu_topic` -> 默认 `/livox/imu`
- `nmea/posit_odo_topic` -> 当前配置里是 `/rtk/gps_odom`
- `gnss/gnss_enable` -> 当前配置为 `false`
- `nmea/nmea_enable` -> 当前配置为 `true`

这一步你要建立一个意识：
- `gnss_enable` 关掉以后，源码里原始 GNSS 观测、星历、伪距、多普勒那条后端不会跑。
- 现在真正参与融合的是 `/rtk/gps_odom` 这个松耦合位置观测。

## 3. 数据怎么进缓冲区

文件：
- [src/LIGO./src/li_initialization.cpp](/home/cclg/muti_path_creater/src/LIGO./src/li_initialization.cpp:1)

核心回调：
- `standard_pcl_cbk()` / `livox_pcl_cbk()`：进 LiDAR 点云。
- `imu_cbk()`：进 IMU。
- `nmea_meas_callback()`：进 `/rtk/gps_odom`。
- `gnss_meas_callback()`：进原始 GNSS 观测。

这里的角色很像“门卫”：
- LiDAR 先进 `lidar_buffer`
- IMU 先进 `imu_deque`
- NMEA 先进 `nmea_meas_buf`
- 原始 GNSS 先进 `gnss_meas_buf`

如果时间戳倒退，代码会直接丢掉当前数据，避免缓存乱序。

## 4. 真正的同步在什么地方

文件：
- [src/LIGO./src/li_initialization.cpp](/home/cclg/muti_path_creater/src/LIGO./src/li_initialization.cpp:369)
- [src/LIGO./src/laserMapping.cpp](/home/cclg/muti_path_creater/src/LIGO./src/laserMapping.cpp:558)

关键函数：
- `sync_packages()`

它做的事不是简单“按时间戳等一下”，而是：
- 取出一帧 LiDAR
- 找到覆盖这帧 LiDAR 时间窗口的 IMU
- 再找同一窗口内的 NMEA 或 GNSS
- 拼成一个 `MeasureGroup`

当前这套配置里最重要的是这句逻辑：
- `LIGO` 不直接拿 `/handsfree/rtk/gnss` 来算地图
- 它拿的是 `gnss_to_enu.py` 输出的 `/rtk/gps_odom`

你读源码时，先看 `sync_packages()`，再看后面的主循环，会顺很多。

## 5. 前端在做什么

文件：
- [src/LIGO./src/preprocess.cpp](/home/cclg/muti_path_creater/src/LIGO./src/preprocess.cpp:1)
- [src/LIGO./src/IMU_Processing.cpp](/home/cclg/muti_path_creater/src/LIGO./src/IMU_Processing.cpp:1)
- [src/LIGO./src/Estimator.cpp](/home/cclg/muti_path_creater/src/LIGO./src/Estimator.cpp:1)
- [src/LIGO./include/ivox/ivox3d.h](/home/cclg/muti_path_creater/src/LIGO./include/ivox/ivox3d.h:1)

前端可以拆成三层：

1. `preprocess.cpp`
   - 把原始点云整理成可用格式
   - 处理不同雷达类型和时间字段

2. `IMU_Processing.cpp`
   - 当前主流程里主要做 IMU 初始化
   - 初始化完成后，把 `Measures.lidar` 复制到 `feats_undistort`
   - 这个函数里没有完成完整的 IMU 前向传播和 LiDAR 去畸变

3. `Estimator.cpp`
   - 做状态估计
   - 负责 LiDAR 和局部地图的对齐
   - 负责把当前状态推到后续优化里

这里还有一个地图容器：
- `include/ivox/` 里的 `iVox`
- 它负责快速近邻查询和增量地图维护

所以前端的职责可以理解为：
- 把“原始传感器流”变成“可稳定估计的局部位姿和局部地图”。

## 6. 后端在做什么

文件：
- [src/LIGO./src/NMEA_Assignment.h](/home/cclg/muti_path_creater/src/LIGO./src/NMEA_Assignment.h:1)
- [src/LIGO./src/NMEA_Assignment.cpp](/home/cclg/muti_path_creater/src/LIGO./src/NMEA_Assignment.cpp:1)
- [src/LIGO./include/nmea_factor/](/home/cclg/muti_path_creater/src/LIGO./include/nmea_factor/)
- [src/LIGO./src/GNSS_Assignment.h](/home/cclg/muti_path_creater/src/LIGO./src/GNSS_Assignment.h:1)
- [src/LIGO./src/GNSS_Assignment.cpp](/home/cclg/muti_path_creater/src/LIGO./src/GNSS_Assignment.cpp:1)
- [src/LIGO./include/gnss_factor/](/home/cclg/muti_path_creater/src/LIGO./include/gnss_factor/)

当前你这套 launch 主要走的是 NMEA 后端：
- `nmea_meas_callback()` 把 `/rtk/gps_odom` 放进缓存
- `NMEAAssignment` 用 `GTSAM::NonlinearFactorGraph + ISAM2` 做滑窗优化
- 因子定义在 `include/nmea_factor/` 下面

如果你把 `gnss_enable` 打开，才会进入原始 GNSS 那条路线：
- `GNSS_Assignment.cpp`
- `include/gnss_factor/`
- 原始伪距、多普勒、星历、RTK 观测会参与优化

简单说：
- 现在跑的是“位置约束后端”
- 不是“原始卫星观测后端”

## 7. 主循环怎么串起来

文件：
- [src/LIGO./src/laserMapping.cpp](/home/cclg/muti_path_creater/src/LIGO./src/laserMapping.cpp:305)

主循环里，顺序大致是：
1. `readParameters(nh)`
2. 建立订阅者和发布者
3. `ros::spinOnce()`
4. `sync_packages()`
5. `p_imu->Process(...)`
6. 点云转交、下采样与按点时间排序
7. 初始化地图
8. 当前帧与局部地图匹配
9. 把 NMEA / GNSS 因子送入后端
10. 发布轨迹、点云和位姿

如果你只想抓主线，先盯住这三个节点：
- `sync_packages()`
- `p_imu->Process(...)`
- `NMEAAssignment::delete_variables(...)` 以及后续 `isam.update(...)`

## 10. 一句话总结

这套 LIGO 的实际数据流是：

**GNSS 先对齐和转 ENU，变成 `/rtk/gps_odom`，再和 LiDAR / IMU 一起进入 `ligo_mapping`，前端负责局部稳定估计，后端用 GTSAM/ISAM2 做 NMEA 或 GNSS 约束优化，最后输出轨迹和地图。**
