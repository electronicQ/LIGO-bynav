#### `li_initialization.cpp` 的整体作用

我现在把 `li_initialization.cpp` 理解成 `laserMapping` 的传感器接入层和缓冲同步层。

它主要做三件事：

- 定义并维护共享缓存，比如 `lidar_buffer`、`imu_deque`、`gnss_meas_buf`、`nmea_meas_buf`
- 实现各类传感器回调，把 LiDAR、IMU、GNSS、NMEA 数据先放进对应缓存
- 通过 `sync_packages()` 按时间窗口取出一组同步后的数据，交给 `laserMapping.cpp` 主循环继续处理

所以它和 `laserMapping.cpp` 的分工可以这样记：

- `li_initialization.cpp`：收数据、存数据、对齐数据
- `laserMapping.cpp`：用同步好的数据做 SLAM

回调函数本身不做真正的建图估计，只负责入缓存；`sync_packages()` 也不做状态估计，只负责同步和打包。只有同步打包成功以后，后面的 IMU 处理、点云去畸变、下采样、LiDAR 地图匹配、NMEA/GNSS 后端融合、地图和轨迹发布才会继续执行。

#### LiDAR / IMU 和 GNSS / NMEA 为什么用不同容器

在 `li_initialization.cpp` 里，这几个核心缓存是这样定义的：

```cpp
std::deque<PointCloudXYZI::Ptr>  lidar_buffer;
std::deque<sensor_msgs::Imu::Ptr> imu_deque;
std::queue<std::vector<ObsPtr>> gnss_meas_buf;
std::queue<nav_msgs::OdometryPtr> nmea_meas_buf;
```

我的理解：

- `lidar_buffer` 和 `imu_deque` 用 `std::deque`
- `gnss_meas_buf` 和 `nmea_meas_buf` 用 `std::queue`

原因是 LiDAR / IMU 的缓存更像“时间序列窗口”，同步时不仅要看最早的数据，也常常要看最新的数据：

```cpp
imu_deque.front();      // 看最早还没处理的 IMU
imu_deque.back();       // 看最新缓存到的 IMU
imu_deque.pop_front();  // 删除已经处理或太旧的 IMU

lidar_buffer.front();      // 取最早还没处理的一帧 LiDAR
lidar_buffer.pop_front();  // 删除已经处理或丢弃的 LiDAR 帧
```

特别是 IMU 同步时，经常要判断：

> 最早 IMU 从哪里开始？最新 IMU 有没有覆盖到当前 LiDAR 帧结束时间？

所以 `deque` 更合适，因为它能方便地访问队头和队尾。

GNSS / NMEA 的缓存更像普通先进先出队列：

```cpp
gnss_meas_buf.push(...);   // 新 GNSS 观测进队尾
gnss_meas_buf.front();     // 看最早还没处理的 GNSS 观测
gnss_meas_buf.pop();       // 删除已经处理或太旧的 GNSS 观测

nmea_meas_buf.push(...);   // 新 NMEA / RTK 里程计进队尾
nmea_meas_buf.front();     // 看最早还没处理的 NMEA 观测
nmea_meas_buf.pop();       // 删除已经处理或太旧的 NMEA 观测
```

它们主要按时间顺序一个个进入、一个个取出，不太需要访问队尾或做复杂窗口操作，所以 `queue` 就够了。

一句话总结：

**LiDAR / IMU 用 `deque`，因为同步时要更灵活地看前后时间；GNSS / NMEA 用 `queue`，因为它们基本按先进先出的顺序消费。**

### 5. 同步与拼帧

`MeasureGroup` 里主要有：

- 当前 LiDAR 点云

GNSS / NMEA 数据不会直接放在 `MeasureGroup` 结构体里，而是通过 `sync_packages()` 的参数分别放进 `p_gnss->gnss_msg` 和 `p_nmea->nmea_msg`。

#### LiDAR 帧结束时间是怎么计算的

在 LiDAR 回调中，代码会同时保存两份信息：

```cpp
lidar_buffer.emplace_back(ptr);
time_buffer.emplace_back(msg->header.stamp.toSec());
```

我的理解：

- `lidar_buffer` 保存当前这一帧点云
- `time_buffer` 保存当前这一帧点云的帧起始绝对时间，单位是秒
- 这两个容器是一一对应的，`lidar_buffer.front()` 和 `time_buffer.front()` 指向同一帧 LiDAR

在预处理之后，点云中每个点的 `curvature` 字段被借用来保存“该点相对当前 LiDAR 帧起点的时间偏移”，单位是毫秒。所以同步时会遍历当前帧点云，找到最大的点时间偏移：

```cpp
double end_time = meas.lidar->points.back().curvature;
for (auto pt: meas.lidar->points)
{
    if (pt.curvature > end_time)
    {
        end_time = pt.curvature;
    }
}
```

然后计算当前 LiDAR 帧结束绝对时间：

```cpp
lidar_end_time = meas.lidar_beg_time + end_time / double(1000);
```

也就是：

```text
LiDAR 帧结束绝对时间(s)
= LiDAR 帧起始绝对时间(s)
+ 当前帧最大点时间偏移(ms) / 1000
```

所以这一帧 LiDAR 的有效时间窗口就是：

```text
[meas.lidar_beg_time, lidar_end_time]
```

后面同步 IMU、GNSS、NMEA 都是围绕这个时间窗口来的。这里遍历所有点找最大 `curvature`，是为了避免点云没有严格按时间排序时，直接用 `points.back()` 得到错误的帧尾时间。

这一步是我理解整套 SLAM 的核心之一，因为后面所有前端和后端操作都建立在“时间对齐正确”这件事上。

#### `preprocess.cpp` 的作用和流程

我现在对 `preprocess.cpp` 的理解更具体了：

- 它不是直接做完整 SLAM，而是先把不同雷达的原始消息整理成统一格式
- 它会把每个点的时间信息统一写进 `curvature`
- 它最终输出的是一个“可同步、可按点时间继续推进处理”的点云

在当前 AVIA 流程里，LiDAR 数据进入 `li_initialization.cpp` 的 `livox_pcl_cbk()` 后，会先调用：

```cpp
p_pre->process(msg, ptr);
```

然后再把结果放入缓冲区：

```cpp
lidar_buffer.emplace_back(ptr);
time_buffer.emplace_back(msg->header.stamp.toSec());
```

我的理解是：

- `preprocess.cpp` 先把 Livox / Ouster / Velodyne / Hesai 的消息统一成 `PointCloudXYZI`
- `lidar_buffer` 存当前这帧处理后的点云
- `time_buffer` 存这一帧点云对应的起始绝对时间
- 后面的 `sync_packages()` 再从这两个缓存里取出同步好的 LiDAR 帧

我还记住一个细节：

- 当前代码里 `preprocess.cpp` 更像“预处理和时间编码”
- `give_feature()` 虽然还在，但主路径里并没有真正走完整的 LOAM 特征提取
- 对 AVIA 来说，真正下游使用的是 `pl_surf` 和其中的时间字段

#### LiDAR 帧是怎么进缓存的

我现在把 `livox_pcl_cbk()` 理解成“LiDAR 回调入口”：

1. 收到一帧 Livox 点云
2. 先调用 `p_pre->process(msg, ptr)`
3. 如果没有开启多帧合并，就直接把 `ptr` 放进 `lidar_buffer`
4. 同时把这帧的 `header.stamp` 放进 `time_buffer`

如果开了 `con_frame`，那就不是每帧立刻进缓存，而是先积攒多帧到 `ptr_con`，等合并窗口满了再一起放入 `lidar_buffer`。

所以我可以这样记：

- `process()` 负责“预处理点云”
- `livox_pcl_cbk()` 负责“接收一帧并送入缓存”
- `sync_packages()` 负责“按时间窗口把缓存拼成可计算的数据包”

#### `IMU_Processing.cpp` 的作用和前后联系

文件：

- [src/LIGO./src/IMU_Processing.cpp](/home/cclg/muti_path_creater/src/LIGO./src/IMU_Processing.cpp:1)
- [src/LIGO./src/IMU_Processing.h](/home/cclg/muti_path_creater/src/LIGO./src/IMU_Processing.h:1)

在 `sync_packages()` 同步成功后，`laserMapping.cpp` 主循环会调用：

```cpp
p_imu->Process(Measures, feats_undistort);
```

我的理解：

- `Measures.lidar` 是当前同步出来的一帧 LiDAR 点云
- `Measures.imu` 是当前 LiDAR 时间窗口内同步出来的一段 IMU 数据
- `feats_undistort` 是后续前端继续使用的点云变量

所以更准确的数据流是：

```text
preprocess.cpp
  给每个点写入相对时间 curvature

li_initialization.cpp
  sync_packages()
  同步 LiDAR / IMU / NMEA，得到 Measures
        ↓
IMU_Processing.cpp
  p_imu->Process(Measures, feats_undistort)
  做 IMU 初始化
  把 Measures.lidar 复制到 feats_undistort
        ↓
laserMapping.cpp
  点云按 curvature 排序
  根据每个点的时间 time_current 推进状态
  遇到 IMU / NMEA / GNSS 时间点就做 predict / update
  遇到 LiDAR 点时间就做 LiDAR 地图匹配更新
        ↓
Estimator.cpp
  提供 ESKF 的状态传播模型
  提供 LiDAR / IMU / NMEA / GNSS 量测模型
```

当前这份代码里，`IMU_Processing.cpp` 的 `Process()` 主要有三种情况：

1. 如果 IMU 还没初始化，就用 `Measures.imu` 计算平均加速度和平均角速度
2. 初始化够了之后，把 `Measures.lidar` 复制到 `feats_undistort`
3. 如果没启用 IMU，也直接把 `Measures.lidar` 复制到 `feats_undistort`

我现在要特别记住：

- `IMU_init()` 初始化阶段并不做复杂积分，只统计 IMU 的平均加速度 `mean_acc` 和平均角速度 `mean_gyr`
- 平均加速度主要用于估计重力方向和初始姿态
- 平均角速度可以作为陀螺仪初始均值理解
- `MAX_INI_COUNT` 是 IMU 初始化累计次数阈值，当前定义为 100

还有一个很重要的源码细节：

```cpp
*cur_pcl_un_ = *(meas.lidar);
```

这不是指针赋值，而是把 `meas.lidar` 指向的点云内容拷贝到 `cur_pcl_un_` 指向的点云对象里。
在 `laserMapping.cpp` 里，`cur_pcl_un_` 对应的就是 `feats_undistort`。

所以实际效果可以理解成：

```text
*feats_undistort = *(Measures.lidar)
```

也就是说，当前版本的 `Process()` 在 IMU 初始化完成后，并没有在这个函数里完成完整的“IMU 前向传播 + 点云去畸变”，而是主要把同步好的 LiDAR 点云转交给后续流程。

这个赋值看起来像多余拷贝，但它有几个工程原因：

- 保持 `ImuProcess::Process()` 的接口统一：输入同步数据，输出后续可用点云
- 保留“输出去畸变点云”的位置，变量名 `feats_undistort` 就体现了这个设计意图
- 深拷贝后，后续如果修改 `feats_undistort`，不会影响原始的 `Measures.lidar`
- 也可能是历史代码简化或调整后留下来的结构

所以我现在对它的阶段性理解是：

```text
IMU_Processing.cpp 当前主流程：
先用 IMU 数据完成初始化；
初始化完成后，把当前 LiDAR 帧传给 laserMapping.cpp；
真正的后续点云下采样、按时间排序、状态推进和地图匹配继续在 laserMapping.cpp 里发生。
```

#### `laserMapping.cpp` 和 `Estimator.cpp` 如何完成状态推进

我现在纠正一个容易误解的地方：

```text
不是 IMU_Processing.cpp 里完成完整的 IMU 前向传播和 LiDAR 去畸变；
而是 laserMapping.cpp 主循环按时间推进状态；
Estimator.cpp 提供状态传播模型和各类量测模型。
```

具体关系是：

- `laserMapping.cpp` 调用 `kf_output.init_dyn_share_modified_3h(...)`，把模型函数注册进 ESKF
- `Estimator.cpp` 的 `get_f_output()` 定义状态如何随时间变化
- `Estimator.cpp` 的 `df_dx_output()` 定义状态传播雅可比
- `Estimator.cpp` 的 `h_model_output()` 定义 LiDAR 点到局部地图平面的残差
- `Estimator.cpp` 的 `h_model_IMU_output()` 定义 IMU 量测残差
- `Estimator.cpp` 的 `h_model_NMEA_output()` / `h_model_GNSS_output()` 定义 NMEA 或 GNSS 约束

LiDAR 点的绝对时间是在 `laserMapping.cpp` 中这样算出来的：

```cpp
time_current = point_body.curvature / 1000.0 + pcl_beg_time;
```

其中：

- `pcl_beg_time` 是当前 LiDAR 帧起始绝对时间
- `point_body.curvature` 是当前点相对帧起点的时间偏移，单位 ms
- `time_current` 就是当前点对应的绝对时间

然后主循环会根据时间差调用：

```cpp
kf_output.predict(dt, Q_output, input_in, true, false);
```

并在不同观测到来时调用不同更新：

```cpp
kf_output.update_iterated_dyn_share_IMU();
kf_output.update_iterated_dyn_share_modified();
kf_output.update_iterated_dyn_share_NMEA();
```

我的理解：

```text
laserMapping.cpp 负责调度：
  什么时候预测
  什么时候用 IMU 更新
  什么时候用 LiDAR 点到地图更新
  什么时候插入 NMEA/GNSS 约束

Estimator.cpp 负责提供模型：
  状态传播模型
  LiDAR 量测模型
  IMU 量测模型
  NMEA/GNSS 量测模型
```

所以我现在把 `laserMapping.cpp` 先理解成这套前端的“总控制台”：

- 它不负责定义滤波方程
- 它负责把各类传感器按时间顺序送进滤波器
- 它负责决定什么时候预测、什么时候更新
- 它还负责 LiDAR 点云的时间排序、去畸变前后的组织、局部地图匹配和输出发布

换句话说：

```text
Estimator.cpp = 写公式的人
laserMapping.cpp = 按时间把公式真正跑起来的人
```

所以我后面整体学习 `laserMapping.cpp` 时，重点不是盯着 IESKF 的每个矩阵推导，而是先看它怎么把整个前端流程串起来：

1. 传感器数据怎么进来
2. LiDAR 帧怎么按时间分段
3. IMU 怎么驱动状态推进
4. LiDAR / GNSS / NMEA 怎么触发更新
5. 地图怎么维护
6. 最终结果怎么发布出去

所以当前代码不是先在 `IMU_Processing.cpp` 里生成一帧完全运动补偿后的点云，而是在 `laserMapping.cpp` 里利用每个点的时间戳，边预测状态，边做 LiDAR 点到地图的匹配更新。

#### 预测模型的三个部分

`Estimator.cpp` 中和预测步骤直接相关的内容主要有三个：

1. `get_f_output()`
2. `df_dx_output()`
3. `process_noise_cov_output()`

`get_f_output()` 返回状态变化率，也就是状态确定性变化的模型：

```text
pos_dot = vel
rot_dot = omg
vel_dot = rot * acc + gravity
```

它用于传播名义状态，可以理解为状态均值如何随时间变化：

```text
x_new = x_old ⊕ f(x, u) * dt
```

`df_dx_output()` 返回状态传播模型对误差状态的雅可比矩阵 `F`，用于传播原有状态不确定性：

```text
P_new = F * P_old * F^T + ...
```

`process_noise_cov_output()` 构造过程噪声协方差 `Q_output`，表示 IMU 噪声、速度噪声和 bias 随机游走等带来的新增不确定性。

当前 `esekfom.hpp` 的 `predict()` 大致执行：

```cpp
if (predict_state)
{
    flatted_state f_ = f(x_, i_in);
    x_.oplus(f_, dt);
}

if (prop_cov)
{
    cov f_x_ = f_x(x_, i_in, dt);
    P_ = f_x_ * P_ * f_x_.transpose() + Q * (dt * dt);
}
```

因此：

```text
get_f_output()
    传播状态确定性部分/名义状态 x

df_dx_output()
    传播原有协方差 P

Q_output
    添加过程噪声造成的不确定性
```

预测中的状态更新和协方差更新可以通过参数分开控制：

```cpp
kf_output.predict(dt, Q_output, input_in, true, false);
// 只更新状态

kf_output.predict(dt, Q_output, input_in, false, true);
// 只传播协方差
```

#### 前端 IESKF 的帧内执行顺序

当前前端不是“等一整帧处理完再统一更新”，而是按时间戳把一帧里的 IMU、NMEA/GNSS 和 LiDAR 点块穿插处理：

```text
IMU 到来
  ↓
predict()
  ↓
NMEA / GNSS 时间点到来
  ↓
先预测到该时刻，再做后端约束和前端观测更新
  ↓
LiDAR 某个时间块到来
  ↓
先预测到该块时刻，再对这一块点云做 LiDAR 更新
```

更具体地说：

- IMU 主要负责高频推进状态
- NMEA / GNSS 会在自己的时间点插入，先把状态推进到该时刻，再触发对应更新
- LiDAR 点云先按时间压成若干块
- 每一块里，`h_model_output()` 会逐个点筛选有效平面约束
- 但真正进入 ESKF 的，是这一块有效点构成的一批残差和雅可比，而不是“每个点单独更新一次状态”

所以可以把它理解成：

```text
点是逐个建模的，状态是按块批量更新的。
```

这其实也是激光雷达里很常见的更新方式。以 FAST-LIO2 的官方实现为例，`h_share_model()` 会遍历当前扫描中的全部有效点，逐点构造残差与雅可比，最后再统一调用一次 `update_iterated_dyn_share_modified()` 完成这一帧的迭代更新；也就是说，它同样是“点级建模，帧级/块级更新”的思路，不是每个点单独触发一次完整滤波更新。

时间只在块级起作用：

```text
时间只在块级起作用
→ 决定用哪个预测状态
→ 决定这一块点云用哪一刻的状态建模

块内逐点建模时
→ 只看点坐标和当前状态
→ 不再单独处理每个点的时间
```

LIGO 和 FAST-LIO2 在这里的思路也不完全一样：

```text
FAST-LIO2:
  更偏向“每点去畸变，再整帧建模”

LIGO:
  更偏向“按小时间块推进状态，块内近似同一参考时刻”
```

这里还要注意一点：这个“块”不是固定时长切出来的，而是由点云里 `curvature` 所代表的时间偏移压缩得到的连续时间片段。名字虽然叫 `feats_undistort`，但当前主流程里并没有做完整的逐点去畸变，而是把块内点近似当作同一参考时刻的观测来处理。

LIGO 这样设计的原因主要有三个：

1. 一帧 LiDAR 不是瞬时采完的，分块后更容易把状态推进到更接近真实采样时刻的位置。
2. 块内近似同一时刻，计算量比每个点都做完整时间补偿和独立更新更可控。
3. 这份代码还要在一帧内部穿插 IMU、NMEA/GNSS 约束，分块更方便把多源观测按时间插进去。
4. 尤其是 NMEA/GNSS 这类非 LiDAR 观测，往往不是严格和每个激光点同步到达的，分块以后更容易在合适的时间点把它们插入滤波流程，而不用把整帧点云完全拆成逐点级别的频繁更新。

所以：

```text
laserMapping.cpp：
  决定什么时候预测、什么时候更新

Estimator.cpp：
  提供预测方程、雅可比和观测模型

esekfom.hpp：
  执行通用 ESKF 的矩阵运算和流形状态更新
```

当前 `init_dyn_share_modified_3h()` 内部设置了：

```cpp
maximum_iter = 1;
```

所以这套代码名义上是迭代误差状态卡尔曼滤波（IESKF），但在当前参数下，更接近“ESKF / IEKF 的一次线性化更新”：

- `update_iterated_dyn_share_modified()` 的接口本身支持迭代
- 但 `maximum_iter = 1`，所以当前实际只做一轮
- 这一轮里会用当前预测状态作为线性化点，调用 `h_model_output()` 生成这一批点的残差和雅可比
- 然后一次性完成 Kalman 修正

所以现在更准确的理解是：

```text
算法框架：迭代误差状态卡尔曼滤波（IESKF）
实际运行：退化成 1 次迭代的 ESKF / IEKF 形式
```

也可以记成：

```text
块内逐点建模
→ 共享同一个预测状态作为线性化点
→ 把所有有效点的观测堆成一批
→ 批量更新状态
```

如果 `maximum_iter > 1`，那么这一批点还会在更新后的状态上重新跑一遍 `h_model_output()`，重新计算残差、雅可比和有效点集合，这才更像完整的 IESKF 迭代过程。

#### 7.1 LIGO 的整体定位

我现在对 LIGO 的整体理解是：

**LIGO 的实时主体仍然是前端 IESKF；NMEA 后端提供全局坐标约束和更一致的当前状态参考。**

前端负责高频实时运行：

```text
IMU / LiDAR / NMEA 按时间处理
        ↓
IESKF 预测与迭代更新
        ↓
得到当前时刻的局部位姿和状态
        ↓
把当前 LiDAR 点转换到 camera_init 局部世界坐标系
```

后端不是直接替代前端，也不是直接优化 `ivox_` 里的体素点，而是把 NMEA 和 LIO 约束放入因子图，得到更一致的状态估计。

#### 7.2 NMEA 如何进入后端因子图

NMEA 数据先由回调函数放入：

```cpp
nmea_meas_buf
```

同步后，在 `laserMapping.cpp` 中按照时间处理。处理 NMEA 时，代码大致是：

```cpp
kf_output.predict(...);                  // 先预测到 NMEA 时间
p_nmea->processNMEA(nmea_cur, kf_output.x_);
update_nmea = p_nmea->Evaluate(kf_output.x_);
```

`processNMEA()` 在初始化阶段会收集 NMEA 位置和当前前端状态，使用 SVD 估计局部轨迹和 ENU 轨迹之间的初始对齐关系。

初始化完成后：

```text
nmea_ready = true
```

后续 NMEA 会进入 `Evaluate()`。`Evaluate()` 主要完成以下工作：

1. 使用当前 `state` 生成当前因子图变量的初值
2. 调用 `AddFactor()` 添加因子
3. 添加 LIO 相对约束或重力、速度、偏置等相关约束
4. 添加 NMEA 绝对位置/姿态/速度约束
5. 调用 `runISAM2opt()` 执行 iSAM2 增量优化
6. 从优化结果中取出当前状态，写入 `state_const_`

NMEA 因子的典型形式是：

```cpp
NMEAFactor(P(0), E(0), A(frame_num), R(frame_num), ...)
```

其中可以这样理解：

```text
P(0)：局部 camera_init 坐标系到 ENU 的旋转对齐变量
E(0)：局部 camera_init 坐标系到 ENU 的平移锚点变量
R(i)：因子图中的第 i 个关键帧姿态
A(i)：因子图中的位置、速度等状态
```

这里的 `R(i)`、`A(i)` 是 GTSAM 因子图内部的变量，不等同于 `pose_graph_key_pose` 这个普通 C++ 容器中的对象。

#### 7.3 iSAM2 优化结果保存在哪里

`runISAM2opt()` 调用：

```cpp
p_assign->isam.update(...);
p_assign->isamCurrentEstimate =
    p_assign->isam.calculateEstimate();
```

因此后端优化结果主要保存在：

```cpp
p_nmea->p_assign->isamCurrentEstimate
```

它是一个 `gtsam::Values`，里面存放因子图变量的当前估计值，包括：

```text
当前活动窗口内的关键帧姿态
当前活动窗口内的位置、速度、bias、重力等状态
P(0)、E(0) 等局部系到 ENU 的对齐变量
```

后端优化不是每次都从第一帧到当前帧做完整批量优化。代码中存在：

```cpp
delete_variables(...)
```

并且通过 `gtsam_variable_thres` 等参数控制旧变量删除或边缘化。因此更准确的说法是：

```text
GTSAM/iSAM2 增量因子图
+
当前活动窗口内的状态优化
+
全局 ENU 对齐变量估计
```

#### 7.4 后端结果如何变成前端 NMEA 观测

后端优化得到的当前状态会被写入：

```cpp
p_nmea->state_const_
```

在 `Evaluate()` 中，代码会把优化结果中的当前姿态、位置、速度等取出来：

```cpp
state_const_.rot = isamCurrentEstimate.at<gtsam::Rot3>(R(frame_num-1)).matrix();
state_const_.pos = isamCurrentEstimate.at<gtsam::Vector6>(A(frame_num-1)).segment<3>(0);
state_const_.vel = isamCurrentEstimate.at<gtsam::Vector6>(A(frame_num-1)).segment<3>(3);
```

然后 `Estimator.cpp` 中的 `h_model_NMEA_output()` 使用 `state_const_` 构造前端 IESKF 的 NMEA 残差：

```cpp
位置残差 = p_nmea->state_const_.pos - s.pos;
速度残差 = p_nmea->state_const_.vel - s.vel;
姿态残差 = Log(s.rot.transpose() * p_nmea->state_const_.rot);
```

最后由：

```cpp
kf_output.update_iterated_dyn_share_NMEA();
```

完成前端 IESKF 更新。

所以两者关系不是简单的：

```cpp
kf_output.x_ = isamCurrentEstimate;
```

而是：

```text
因子图优化结果
        ↓
state_const_，作为 NMEA 参考状态
        ↓
h_model_NMEA_output() 构造残差和雅可比
        ↓
IESKF 计算 Kalman 增益
        ↓
更新 kf_output.x_ 和 kf_output.P_
```

因此，后端结果会影响当前前端状态，也会影响后续 IMU 预测和 LiDAR 更新。

#### 7.5 后端优化和历史关键帧缓存的关系

后端因子图内部有自己的关键帧变量，例如：

```text
R(i)、A(i)、F(i)、O(i)、G(i)
```

同时，程序还维护了用于轨迹和地图重建的缓存：

```cpp
std::vector<curvefitter::PoseData> pose_graph_key_pose;
std::vector<double> pose_time_vector;
std::vector<std::vector<Eigen::Vector3d>> LiDAR_points;
```

这两组数据不是同一回事：

```text
因子图内部变量：
    被 GTSAM/iSAM2 优化

pose_graph_key_pose：
    laserMapping.cpp 中的关键帧位姿缓存

LiDAR_points：
    每个缓存关键帧对应的局部 body/IMU 坐标点

pose_time_vector：
    缓存关键帧时间
```

因子图优化不会自动把所有结果逐个写回 `pose_graph_key_pose[i]`，也不会自动修改 `LiDAR_points[i][j]`。如果代码需要重建一段历史地图，会使用新的轨迹重新计算：

```cpp
Eigen::Vector3d mappoint = pose * LiDAR_points[i][j];
```

得到新的世界坐标点 `updatedmap`，再把这些点加入新的体素地图。

#### 7.6 `ivox_` 在后端流程中的位置

```cpp
std::shared_ptr<IVoxType> ivox_;
```

`ivox_` 是前端最近邻搜索和点到平面匹配使用的增量体素地图：

```text
当前 LiDAR 点
        ↓
根据 kf_output.x_ 转到 camera_init/world
        ↓
在 ivox_ 中搜索邻域点
        ↓
拟合局部平面
        ↓
构造 LiDAR 点到平面残差
```

它不是因子图的优化变量，因子图不会直接优化其中的体素或地图点。

当前 `IVox` 默认有：

```cpp
resolution_ = 0.2;
capacity_ = 1000000;
```

实际参数由：

```yaml
mapping/ivox_grid_resolution
```

读取。`capacity_` 表示最多保存的体素数量，不是最多保存的点数量。达到容量后，旧体素会从 `grids_cache_` 尾部删除，所以 `ivox_` 是有容量限制的活动地图，而不是无限增长的全局历史地图。

#### 7.7 后端修正后是否重建局部体素地图

设计上的完整逻辑可以理解为：

```text
NMEA/GNSS 后端优化
        ↓
IESKF 使用后端结果更新当前状态
        ↓
比较更新前后的当前位姿
        ↓
修正较小：继续使用原 ivox_
修正较大：重新拟合缓存轨迹
        ↓
用新轨迹重新变换 LiDAR_points
        ↓
得到 updatedmap
        ↓
构造或更新 ivox_last_
        ↓
将修正后的地图交给 ivox_
```

在代码中，GNSS 分支对这个逻辑实现得比较完整，例如：

```cpp
if ((out_state.pos - kf_output.x_.pos).norm() > 0.1
    && pose_graph_key_pose.size() > 4)
{
    traj_manager->FitCurve(...);
    updatedmap = traj_manager->GetUpdatedMapPoints(...);
    ivox_last_->AddPoints(updatedmap);
    ivox_->grids_map_ = ivox_last_->grids_map_;
}
```

但是，当前 `laserMapping.cpp` 的 NMEA 分支主要明确执行的是：

```cpp
p_nmea->Evaluate(kf_output.x_);
kf_output.update_iterated_dyn_share_NMEA();
```

并打印 NMEA 更新前后的状态差异。不能把 GNSS 分支中完整的地图重建代码，直接当成当前 NMEA 分支每次都会执行的行为。学习源码时要以实际分支为准：

```text
NMEA 后端优化：确定会发生
NMEA 结果作为 IESKF 观测：确定会发生
NMEA 分支每次都重建 ivox_：当前源码不能这样概括
```

#### 7.8 局部世界坐标地图的保存逻辑

当前地图保存的主要变量是：

```cpp
PointCloudXYZI::Ptr pcl_wait_save;
```

每帧 LiDAR 经过前端状态变换：

```cpp
pointBodyToWorld(...);
```

得到：

```cpp
feats_down_world
```

它已经是 `camera_init` 局部世界坐标系下的点云。随后在 `publish_frame_world()` 中累加：

```cpp
*pcl_wait_save += *laserCloudWorld;
```

因此当前保存地图的基本数据流是：

```text
前端 IESKF 当前状态 kf_output.x_
        ↓
当前 LiDAR 点变换到 camera_init
        ↓
feats_down_world
        ↓
pcl_wait_save 逐帧累加
        ↓
保存局部世界坐标 PCD
```

这条保存路径不等同于：

```text
因子图优化全部历史关键帧
        ↓
逐帧回写 pcl_wait_save
```

当前已经累加到 `pcl_wait_save` 的历史点，不会因为后端因子图优化而自动按照每个历史关键帧重新回拉。后端主要影响当前 `kf_output.x_` 以及后续新加入的点。

如果开启了周期性 PCD 保存，代码会把 `pcl_wait_save` 写盘后清空：

```cpp
pcd_writer.writeBinary(..., *pcl_wait_save);
pcl_wait_save->clear();
```

已经写入磁盘的点云更不会在当前程序中被自动回溯修改。

#### 7.9 最终保存到 ENU 坐标系

程序结束保存剩余点云时，如果 NMEA 因子图有有效结果，会从：

```cpp
isamCurrentEstimate
```

中取出：

```cpp
P(0)
E(0)
```

构造局部 `camera_init` 到 ENU 的变换：

```cpp
final_transform.block<3, 3>(0, 0) = enu_rot;
final_transform.block<3, 1>(0, 3) = anc_cur;
```

然后对 `pcl_wait_save` 中的局部世界点做一次整体变换：

```cpp
pcl::transformPointCloud(
    *pcl_wait_save,
    *pcl_enu_save,
    final_transform
);
```

所以最终保存有两种情况：

```text
没有有效 NMEA 后端结果：
    保存 camera_init 局部世界坐标地图

有有效 NMEA 后端结果：
    将 camera_init 局部世界坐标地图整体变换到 ENU
    保存 scans_Global_ENU.pcd
```

这里的整体 ENU 变换不是重新优化每个历史点，而是给已经生成好的局部地图统一乘一个坐标变换。

#### 7.10 后端部分的总数据流

当前 LIGO 可以用下面这条链路概括：

```text
LiDAR / IMU / NMEA 回调
        ↓
各自缓存
        ↓
sync_packages() 按 LiDAR 时间窗口同步
        ↓
laserMapping.cpp 按时间处理
        ↓
IESKF predict
        ↓
IMU / LiDAR 观测更新
        ↓
当前状态生成 camera_init 局部世界点
        ↓
累加到 pcl_wait_save 和/或加入 ivox_

NMEA 到来
        ↓
Evaluate()
        ↓
加入 LIO 因子和 NMEA 因子
        ↓
iSAM2 增量优化
        ↓
得到 isamCurrentEstimate
        ↓
提取当前优化状态到 state_const_
        ↓
h_model_NMEA_output()
        ↓
IESKF NMEA 迭代更新 kf_output.x_
        ↓
影响当前和后续前端状态

程序结束保存
        ↓
局部 camera_init 点云保持前端累加结果
        ↓
若有后端 P(0)/E(0)，整体变换到 ENU
        ↓
写入最终 PCD
```

我的最终理解是：

**LIGO 不是 LIO-SAM 那种把后端优化后的整条历史轨迹逐个回写，再统一重建全局地图的典型架构。它主要依赖前端 IESKF 实时建图；NMEA 通过后端因子图生成更准确的当前状态参考，再回灌前端。局部地图是否重建取决于具体代码分支，最终 ENU 保存则使用后端估计的局部系到 ENU 变换。**

## 二、系统和程序小知识

### 1. 一个节点和一个进程

我的理解：

- ROS 里的 `node` 是逻辑通信单元
- 操作系统里的 `process` 是实际运行实例
- 在 `roslaunch` 中，一个 `<node>` 通常对应一个独立进程

所以这套系统里：

- LiDAR 驱动通常是一个进程
- IMU 驱动通常是一个进程
- GNSS 驱动通常是一个进程
- `ligo_mapping` 也是一个独立进程

### 2. 多线程和共享变量

我的理解：

- 一个进程里可以有多个线程
- `ligo_mapping` 使用了 `ros::AsyncSpinner`
- 所以回调线程和主循环线程可能并发访问同一份全局变量

因此：

- 只读配置通常不需要频繁加锁
- 缓冲队列、时间戳、运行状态这些会被并发读写，原则上要加锁
- 这个工程里已经对一部分共享状态加了锁，但不是所有变量都严格原子化

### 3. `AsyncSpinner` 和回调线程

我的理解：

- `ros::AsyncSpinner spinner(0); spinner.start();` 启动的是一个回调线程池
- `0` 不是“0 个线程”，而是让 ROS 按 CPU 核心数自动决定线程数
- 它不是“一个回调一个线程”，而是多个线程共享一个回调队列
- 哪个线程空闲，就去队列里取一个回调来执行

更直白地说：

- 多个回调任务排成一个队列
- 多个线程组成一个线程池
- 这个线程池共同处理这一个队列
- 不是一个线程池去处理多个队列，也不是一个回调对应一个线程

所以：

- 如果只有 1 个线程，而这个线程正在处理一个耗时回调，后面的回调就要排队等它
- `ros::spinOnce()` 不是回调启动开关，只是主线程顺手处理一轮当前可用回调
- 在已经用了 `AsyncSpinner` 的节点里，`spinOnce()` 往往是可有可无的

### 4. `extern` 的作用

我的理解：

- `parameters.h` 里写 `extern`，表示这里只声明，不定义
- `parameters.cpp` 里才是真正定义这些全局变量的地方
- 所有 include 这个头文件的 `.cpp`，在同一个进程里都能访问同一份变量

这就是为什么这个文件叫 `parameters`，但它实际上不只是参数，还承担了“全局共享状态中心”的角色。

### 5. ROS 参数和代码参数

我的理解：

- `launch` / `yaml` 里写的是运行配置
- `readParameters()` 把这些配置读进代码
- 之后程序内部多数地方直接读全局变量，不再重复查 ROS parameter server

### 6. 我现在最重要的学习习惯

我准备每次都按这个顺序看：

1. 先看 launch
2. 再看参数文件
3. 再看回调
4. 再看同步函数
5. 再看前端处理
6. 最后看后端优化

这样不会一上来就被大文件淹没。
